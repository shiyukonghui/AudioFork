### 概述

本规划将整个项目分解为四个递进阶段，每个阶段产出可验证的里程碑。阶段之间遵循"基础设施→核心管道→高级特性→GUI与打磨"的依赖链，确保每一阶段的交付物都可独立测试。

| 阶段 | 主题 | 预计核心产出 |
|------|------|-------------|
| 第一阶段 | 音频基础设施 | 设备枚举、CLI 全参数骨架、统一错误类型、同参数单路直通验证 |
| 第二阶段 | 核心分发管道 | 扇出模型、无锁队列、声道映射、欠载/溢出处理、启动/停止状态机 |
| 第三阶段 | 高级鲁棒性 | 重采样、时钟漂移补偿、WASAPI 独占模式、热插拔、输入丢失恢复、限幅器 |
| 第四阶段 | GUI 与打磨 | egui 前端、消息通道解耦、panic 隔离、完整交互、跨平台打包 |

### 阶段准入准出标准（Stage-Gate）

| 阶段 | 准入门槛 | 准出条件 |
|------|----------|----------|
| 第一阶段 | `cargo init` 完成，依赖声明就绪 | 全部 A1.x 验收通过 |

| 第四阶段 | 第三阶段准出 + `egui` 框架选型确认 | 全部 A4.x 验收通过 |

### 第一阶段：音频基础设施

**目标**：搭建 Rust 工程骨架，实现基本的音频设备枚举和单路直通播放，验证 `cpal` 在目标平台上的可用性。

#### 1.1 工程初始化

- 使用 `cargo init` 创建 Rust 项目，配置 `Cargo.toml`。
- 引入依赖：
  - `cpal` — 跨平台音频 IO
  - `clap`（或 `lexopt`）— CLI 参数解析
  - `toml` + `serde` — 配置文件读写
  - `log` + `tracing` + `tracing-subscriber` + `tracing-appender` — 日志基础设施（含文件日志）
- **编译时特性（Cargo features）**：
  ```toml
  [features]
  default = []
  wasapi-exclusive = ["dep:wasapi-rs"]   # Windows 独占模式，仅编译时启用
  ```
  - `--wasapi-exclusive` 参数仅在启用该 feature 且目标平台为 Windows 时可用，其他平台编译时该参数不可见（`#[cfg(feature = "wasapi-exclusive")]`）。
- 建立 `src/` 目录模块划分：
  ```
  src/
  ├── main.rs          // 入口
  ├── cli.rs           // CLI 参数定义与解析
  ├── config.rs        // 配置文件结构体与读写
  ├── device.rs        // 设备枚举与选择
  ├── audio/
  │   ├── mod.rs
  │   ├── capture.rs   // 输入流封装
  │   └── playback.rs  // 输出流封装
  └── error.rs         // 统一错误类型（见 1.6）
  ```
- `config.rs` 配置结构体需包含 `gui_enabled: bool` 字段（对应需求说明书 §6 示例），用于控制默认启动模式（CLI 或 GUI）。

#### 1.2 设备枚举模块

- 实现 `enumerate_input_devices()` / `enumerate_output_devices()`：
  - 调用 `cpal` 获取设备列表。
  - 返回设备名称、默认采样率范围、声道数范围、支持的格式列表。
  - **标记设备类型**：在返回信息中加入 `DeviceType` 枚举（`Wired` / `Bluetooth` / `Network` / `Unknown`），通过设备名称关键字和系统接口推断。
- 实现 `select_input_device(name: Option<&str>) -> Result<Device>`：
  - 若 `None`，返回系统默认输入设备。
  - 若 `Some`，按名称模糊匹配（**名称含指定字符串即可**）。
- 实现 `select_output_devices(names: &[String]) -> Result<Vec<Device>>`：
  - 若列表为空，返回所有有效输出设备（包含蓝牙/网络设备，保证分发覆盖）。
  - 过滤无效设备（如纯输入设备）。
- **蓝牙/网络设备策略**：
  - 枚举时**默认包含**蓝牙与网络音频设备，确保"仍可分发"（需求说明书 §5）。
  - 在设备信息结构中附加 `device_type` 字段，CLI 日志输出时标注 `[蓝牙]`/`[网络]` 提示高延迟。
  - GUI 中蓝牙/网络设备默认选中但以警告图标标注"高延迟设备"。
  - 第一阶段暂不提供 `--exclude-bluetooth`，留待后续评估后加入（若需要）。

#### 1.3 CLI 骨架

- 定义完整命令行参数结构体 `CliArgs`（需求说明书 2.1），覆盖以下所有参数：
  - `--input-device <NAME>`
  - `--output-device <NAME>`（可多次指定）
  - `--sample-rate <HZ>`
  - `--channels <NUM>`
  - `--buffer-frames <FRAMES>`
  - `--max-latency-ms <MS>`
  - `--resampler {sinc|cubic|none}`
  - `--no-drift-compensation`
  - `--exit-on-input-loss`
  - `--input-fallback-to-default`
  - `--log-file <PATH>`
  - `--monitor`
  - `--wasapi-exclusive`
  - `--gui`
  - `--config <PATH>`
  - `--preset <FILE>`
- **互斥约束**：
  - `--gui` 与 `--monitor` 互斥，同时指定时拒绝启动并提示（GUI 内置状态显示，不输出 JSON 到 stdout）。
- 支持 `--config <PATH>` 加载 TOML 配置文件，命令行参数覆盖配置文件。
- `--preset <FILE>` 导入预设配置文件（格式同 `audio_router.toml`），与 `--config` 作用相同但语义用于 GUI File 菜单导入。
- 实现参数校验（第一阶段仅校验基本类型和解耦约束，第二阶段加入完整校验）。
- **GUI 模式下的参数过滤**（需求说明书 2.10）：若 `--gui` 生效，仅解析 `--config` 和 `--gui` 两个参数，其余命令行参数忽略并输出 `warn!` 日志提示"GUI 模式下该参数无效，请通过界面配置"。

#### 1.4 单路直通验证（仅同参数）

- 使用 `cpal` 创建输入流和**一个**输出流。
- 输入回调接收 `&[f32]`，直接拷贝至输出缓冲区。
- **第一阶段约束**：仅验证输入/输出采样率和声道数**相同**场景下的直通播放。
- **明确不引入 `rubato`**：
  - 若用户指定的输入/输出参数不匹配，第一阶段拒绝启动并提示"需要重采样能力，将在第三阶段支持"。
  - `rubato` 技术预研可在第一阶段末期作为独立子任务进行，但不进入生产代码。
- 支持 Ctrl+C 优雅停止。
- **验证点**：在 Windows 和 macOS 上分别运行，确认能听到来自麦克风/系统音频的回放。

#### 1.5 错误处理架构设计

对应需求说明书 2.6 的三类错误策略，在第一阶段建立统一错误基础设施：

- **统一错误类型 `AudioRouterError`**（定义于 `error.rs`）：
  - `DeviceNotFound(String)` — 设备未找到
  - `StreamError(String)` — 音频流错误（输入/输出）
  - `ConfigError(String)` — 配置/参数错误
  - `Fatal(String)` — 致命错误，立即退出
  - `ChannelError(String)` — 消息通道错误
- **错误严重级别**（`ErrorSeverity` 枚举）：
  - `Recoverable` — 可恢复（如输出流断开，槽位停用）
  - `Degraded` — 降级运行（如输入流断开，静音输出并重连）
  - `Fatal` — 致命（立即退出进程）
- **错误恢复状态机**（框架，第三阶段完整实现）：
  - 定义 `RecoveryState` 枚举：`Normal` / `ReconnectBackoff { attempt, next_interval }` / `FallbackToDefault`。
  - 第一阶段仅定义状态枚举和 API 签名，不实现具体恢复逻辑。
- 所有模块通过统一的 `Result<T, AudioRouterError>` 返回错误。

#### 1.6 第一阶段验收标准

| 编号 | 验收项 | 验证方式 |
|------|--------|----------|
| A1.1 | 正确枚举所有输入/输出设备 | 打印设备列表，与系统音频设置对比 |
| A1.2 | `--input-device` / `--output-device` 正确筛选 | 指定已知设备名启动 |
| A1.3 | 配置文件正确加载，命令行可覆盖 | 设置不同值分别测试 |
| A1.4 | 同参数单路直通延迟 < 20ms（共享模式） | 使用音频分析工具或环路测试 |
| A1.5 | Ctrl+C 后 2 秒内干净退出 | 连续启动/停止 10 次无异常 |
| A1.6 | 不同参数拒绝启动并给出清晰错误 | 指定不匹配的采样率/声道输入输出组合 |
| A1.7 | 蓝牙/网络设备被枚举并标记类型 | 连接蓝牙音箱后运行，检查日志输出设备类型 |
| A1.8 | `error.rs` 中定义统一错误类型、严重级别、恢复状态枚举 | 代码审查验证 |

### 第二阶段：核心分发管道

**目标**：实现扇出（fan-out）架构，将一路输入同时分发至多个输出设备，并处理声道映射与欠载/溢出。

#### 2.1 SPSC 无锁队列集成

- 引入 `ringbuf` 库，创建 `Ringbuf<T>` 的 `Producer` / `Consumer` 对。
- 封装为 `Slot` 结构体：
  ```rust
  struct Slot {
      producer: Option<RingbufProducer<f32>>,
      active: AtomicBool,
  }
  ```
- 常量 `MAX_OUTPUTS = 32`。

#### 2.2 槽位管理

- 实现 `SlotArray`（固定大小数组 + 原子操作）：
  - `allocate_slot(producer) -> Option<usize>`：寻找空闲槽位（`active == false`），先填充 `producer`，再 `store(true, Release)`。
  - `deactivate_slot(index)`：`store(false, Release)`，**保留 Producer 不释放**（延迟释放策略）。
  - `iter_active()`：`Acquire` 读取 `active` 标志，仅返回活跃槽位的 `Producer`。

#### 2.3 输入采集回调（扇出写入）

- 实现输入回调闭包：
  1. 遍历 `SlotArray.iter_active()`。
  2. 对每个活跃 `Producer`，检查 SPSC 剩余空间。
  3. 空间足够 → 写入全部帧。
  4. 空间不足 → 丢弃整帧，递增 `overflow_count`（`AtomicU64`）。
- **关键约束**：回调内零堆分配、零锁、仅使用 `Acquire` 原子读和 SPSC 写入。

#### 2.4 输出播放回调（每设备独立）

- 每个活跃输出设备拥有独立线程和输出回调。
- 回调流程：
  1. 计算需求帧数 `N_in_target = ceil(N_out * ratio)`（暂不加重采样和漂移补偿）。
  2. 检查 SPSC 可读样本数。
  3. 足够 → 取出样本，执行声道映射，写入输出缓冲区。
  4. 不足 → 执行欠载处理（见 2.7）。

#### 2.5 声道映射（遵循 ITU-R BS.775）

- 实现 `ChannelMapper` 结构体，根据输入/输出声道数自动选择策略，公式遵循 **ITU-R BS.775** 标准：
  - 立体声 → 单声道：`Mono = 0.5*L + 0.5*R`
  - 5.1 → 立体声：`L' = 0.5*L + 0.35*C + 0.35*Ls`，`R' = 0.5*R + 0.35*C + 0.35*Rs`
  - 单声道 → 立体声：`L = Mono, R = Mono`
  - 其他组合 → 通用映射（按标准声道顺序，多余丢弃，不足填 0）
- 声道相同时跳过映射（零开销）。
- 在模块文档注释中引用 `ITU-R BS.775` 标准，确保公式可追溯。

#### 2.6 智能直通模式

- 输出流创建时判断：
  - **第二阶段的直通条件**：输入采样率 == 输出采样率 && 声道数相同。
  - **注意**：第二阶段尚未实现漂移补偿，因此直通条件中暂不包含"未启用漂移补偿"，等价于第二阶段默认 `--no-drift-compensation=true`。
  - **第三阶段接入漂移补偿后**，直通条件扩展为：输入采样率 == 输出采样率 && 声道数相同 && 未启用漂移补偿。
- 若成立 → 标记为**直通模式**：数据从 SPSC 直接拷贝至输出缓冲区，跳过映射和重采样。
- 否则 → **转换模式**。

#### 2.7 欠载与溢出平缓处理

- **溢出**（生产者侧）：丢弃整帧，不做平滑（输出端后续产生欠载）。
- **欠载**（消费者侧）：
  - 预计算 256 点余弦窗表，线性插值查表。
  - `fade_len = min(5ms 等效帧数, callback_duration / 2)`。
  - **直通模式**：可用帧 > 0 时对最后 `fade_len` 帧淡出后静音；恢复时从静音淡入。
  - **转换模式**：可用帧不足 `N_in_target` 直接输出静音，标记欠载。
- 恢复时执行对称余弦淡入。

#### 2.8 错误回调与槽位停用

对应需求说明书 2.6 的"输出流错误"处理策略：

- **输出流错误回调**：当 `cpal` 的输出流触发错误回调时：
  1. 从错误信息中解析对应的槽位索引（通过建立流→槽位的映射表）。
  2. 调用 `deactivate_slot(index)` 将 `active` 置为 false。
  3. 记录错误日志（`tracing::error!`），包含设备名和错误原因。
  4. （如在 GUI 模式下）通过消息通道推送 `EngineToGui::Error` 事件。
- **输入流错误回调**（框架预留，第三阶段完整实现，见 3.4）：
  1. 设置全局 `input_lost: AtomicBool` 标志。
  2. 所有输出回调检测此标志后执行静音淡出。
  3. 通知控制线程启动重连状态机。

#### 2.9 启动/停止流程

- **启动**：
  1. 解析参数和配置
  2. 初始化输入设备（获取采样率、声道数、缓冲区帧数）
  3. 参数校验（含 `--max-latency-ms` 校验）
  4. 枚举输出设备，为每个设备分配槽位、创建 SPSC 队列
  5. 创建所有输出流（每个流持有独立的 `Consumer`）
  6. **等待就绪**（`AtomicBool` 就绪标志，最多等待 **5 秒**）：
     - 主线程轮询所有输出流的就绪标志（每次轮询间隔 50ms）。
     - 若某设备在 5 秒内未就绪：
       1. 调用 `deactivate_slot(index)` 释放该槽位。
       2. 记录 `tracing::error!("设备 {} 启动超时，已跳过", device_name)`。
       3. 若在 GUI 模式，通过消息通道推送 `EngineToGui::Error` 通知 UI 刷新设备列表并展示错误。
       4. 其余已就绪设备继续启动流程。
     - 若所有设备均超时 → 视为致命错误，退出并提示"无可用的输出设备"。
  7. 启动输入流
- **停止**：
  1. 停止输入流
  2. 等待所有输出流完成淡出（`fade_complete` 标志，轮询间隔 50ms，**2 秒超时**）
  3. 超时设备强制 `pause()` 并释放资源
  4. 输出最终统计

#### 2.10 第二阶段验收标准

| 编号 | 验收项 | 验证方式 |
|------|--------|----------|
| A2.1 | 3 个以上输出设备同时发声 | 实际连接多个音频设备测试 |
| A2.2 | 各输出同步误差 < 缓冲帧数时长 | 录制多设备输出并对齐波形 |
| A2.3 | 声道映射正确（ITU-R BS.775） | 输入 5.1 测试信号，验证立体声输出电平 |
| A2.4 | 欠载/溢出时无爆音 | 人为制造欠载（大缓冲区→小缓冲区切换） |
| A2.5 | 直通模式延迟 < 10ms | 测量 48kHz/128 帧配置 |
| A2.6 | `--max-latency-ms` 校验生效 | 设置不合理值确认拒绝启动 |
| A2.7 | 输出设备启动超时后跳过并继续 | 模拟一个输出流不触发就绪标志，验证其余设备正常播放 |
| A2.8 | 停止流程 2 秒内完成淡出并干净退出 | 运行时发送 Ctrl+C，计时验证无残留线程 |

### 第三阶段：高级鲁棒性

**目标**：集成重采样、时钟漂移补偿、WASAPI 独占模式、设备热插拔、输入丢失恢复、砖墙限幅器，达成 7×24 小时稳定运行。

#### 3.1 重采样集成

- 引入 `rubato` 库，使用 `SincFixedIn`（sinc）和 `Cubic` 重采样器。
- 每个转换模式的输出流持有独立的重采样器实例。
- 重采样器状态管理：
  - `resampler_clean` 标志跟踪状态连续性。
  - 欠载后重置：注入 `filter_delay` 个零样本帧（或调用 `reset()`），再处理真实数据。
- `--resampler none` 且采样率不同 → 启动报错退出。
- 参数校验：GUI 中对应选项同样生效。

#### 3.2 时钟漂移补偿（帧数微调法）

- 每个输出流维护缓冲区水位的 EMA（指数移动平均，时间常数 3s）。
- 控制线程每 100ms 采集水位，与目标水位（缓冲区容量一半）比较。
- PI 控制器计算帧数增量 `delta`（通常 -1/0/+1，整数）。
- `delta` 通过 `AtomicI32` 传递给输出回调，回调据此调整 `N_in_target`。
- `--no-drift-compensation` 时 `delta` 固定为 0。
- **对直通模式的影响**：漂移补偿启用后，即使采样率和声道数相同，也必须退出直通模式（因 `delta` 调整消费帧数），转为转换模式的最小路径（仅微调帧数，不加重采样）。
- **验证**：长时间运行下各输出缓冲区水位稳定在 40%~60% 区间。

#### 3.3 设备热插拔与 WASAPI 独占模式

##### Windows 热插拔

- 使用 `wasapi-rs` / 底层 WASAPI 的 `IMMNotificationClient` 监听设备变更。
- 设备到达事件 → 分配空闲槽位，创建队列和输出流，立即参与分发。
- 设备移除事件 → 对应槽位 `active` 置 false。

##### macOS 热插拔

- 使用 `coreaudio-rs` 注册 `kAudioHardwarePropertyDevices` 监听。
- 到达/移除逻辑同上。

##### 跨平台抽象

- 定义 `DeviceNotifier` trait，平台特定实现：
  ```rust
  trait DeviceNotifier {
      fn start(&mut self, on_add: Box<dyn Fn(DeviceInfo)>, on_remove: Box<dyn Fn(String)>);
  }
  ```

##### WASAPI 独占模式（Windows 特性，编译时 feature）

对应需求说明书 3.1 理想延迟目标（< 10ms）：

- **编译时条件**：该功能通过 `Cargo.toml` 的 `wasapi-exclusive` feature 控制（见 1.1 节），仅在 Windows 目标平台可用。所有独占模式相关代码使用 `#[cfg(feature = "wasapi-exclusive")]` 条件编译，其他平台该代码路径不可见。
- 在输出流创建时，若 `--wasapi-exclusive` 指定且 feature 已启用，尝试使用 `wasapi-rs` 创建独占模式输出流。
- **互斥校验**：
  - 独占模式与共享模式不可混用：若部分设备支持独占而部分不支持，拒绝启动或自动降级为共享模式。
  - 独占模式下强制使用 48kHz / 立体声 / 128 帧配置（或用户指定的采样率，但需设备支持）。
- **独占模式的输出流创建独立于热插拔代码路径**：
  - 独占模式流基于 `wasapi-rs` 创建，而非 `cpal`。
  - 非独占模式继续使用 `cpal` 共享流。
- **停止与恢复**：独占模式流在设备被其他应用占用时触发错误回调，按输出流错误处理流程（2.8）停用槽位。
- **验证**：独占模式下 48kHz/128 帧端到端延迟 < 10ms。

#### 3.4 输入设备丢失恢复（状态机实现）

- **状态机枚举**（在 `error.rs` 1.5 中已定义框架，此阶段完整实现）：
  ```rust
  enum RecoveryState {
      Normal,
      ReconnectBackoff { attempt: u32, next_interval: Duration },
      FallbackToDefault { attempt: u32 },
  }
  ```
- **阶段 1（0~30 秒，指数退避重连原设备）**：
  - 状态：`ReconnectBackoff { attempt, next_interval }`
  - 初始间隔 100ms，每次重连失败后 ×2，最大 5s。
  - 累计 30s 后转入阶段 2。
  - 每次重连尝试之间通过条件变量或计时器精确等待 `next_interval`。
- **阶段 2（30 秒后）**：
  - 若 `--input-fallback-to-default` 为 true → 状态切换至 `FallbackToDefault`，主动调用 `cpal::default_input_device()` 获取当前系统默认设备并尝试连接。
  - 每次尝试间隔 5s。
  - 若 `--input-fallback-to-default` 为 false → 保持 `ReconnectBackoff`，间隔固定 5s 继续尝试原设备。
- **输出端行为**：整个重连期间，所有输出回调通过 `input_lost: AtomicBool` 感知状态，执行静音淡出。
- `--exit-on-input-loss` → 跳过状态机，执行平滑退出：
  1. 设置全局 `input_lost` 标志，通知所有输出回调开始静音淡出。
  2. 等待所有输出流完成淡出（`fade_complete` 标志，最多 2 秒超时）。
  3. 超时设备强制 `pause()`。
  4. 进程 `std::process::exit(0)` 退出。

#### 3.5 砖墙限幅器

- 默认启用，阈值 0dBFS，零攻击（attack=0），10ms 释放。
- **插入点**：声道映射之后、重采样之前（即对映射后的音频帧做限幅，再送入重采样器或直接写入输出缓冲区）。
- `--no-limiter` 可禁用。
- 实现为简单的峰值包络检测 + 增益衰减。

#### 3.6 统计与监控（CLI 模式）

- `--monitor` 启用时，每 5 秒输出 JSON 行至 stdout：
  ```json
  {"ts":1234567890,"outputs":[{"name":"Speakers","underruns":0,"overflows":0,"latency_ms":8.2,"delta":0,"water_level_pct":48}]}
  ```
- 包含：设备名、欠载计数、溢出计数、当前延迟估计、漂移 delta、水位百分比（0~100%）。
- **与 GUI 的互斥行为**：
  - 若同时指定 `--gui` 和 `--monitor`，启动时拒绝并提示错误。
  - GUI 模式下（`--gui` 生效），统计信息通过 `EngineToGui::OutputStatus` 消息通道推送至状态栏显示，不输出 JSON 到 stdout。
  - 命令行模式（`--monitor` 单独使用），JSON 行输出至 stdout，可通过管道重定向。

### 第四阶段：GUI 与打磨

**目标**：基于 `egui` 构建图形界面，通过消息通道与核心引擎解耦交互，实现 panic 隔离，完成跨平台打包。

#### 4.1 GUI 框架搭建与 Panic 隔离

- 引入 `egui` + `eframe`（或 `egui-winit` + `egui-wgpu`/`glow`）。
- 引入 `rfd` — 原生文件对话框（用于配置导入/导出、panic 错误弹窗）。
- 创建 `gui/` 模块：
  ```
  src/
  ├── gui/
  │   ├── mod.rs        // GUI 入口，App trait 实现
  │   ├── panels/
  │   │   ├── mod.rs
  │   │   ├── toolbar.rs     // 顶部工具栏
  │   │   ├── devices.rs     // 左侧设备管理面板
  │   │   ├── params.rs      // 右侧参数配置面板
  │   │   ├── status.rs      // 底部状态栏
  │   │   └── logs.rs        // 日志/事件区域
  │   └── theme.rs           // 浅色/深色主题
  ```
- GUI 以 30 FPS 刷新（`egui::Context::request_repaint_after`）。
- **可访问性与主题**（需求说明书 3.4）：
  - 所有交互控件支持 Tab 键焦点导航和 Enter/Space 键激活（`egui` 默认支持，需确保自定义控件同样实现）。
  - `theme.rs` 实现自动检测系统主题：Windows 通过 `DWM` 注册表查询 / macOS 通过 `NSAppearance`；启动时设置 `egui::Visuals` 为 `light` 或 `dark` 模式，运行时可通过设置菜单手动切换。
  - 主题变更响应延迟 < 200ms。
- **GUI panic 隔离**（对应需求说明书 3.3）：
  - 使用 `std::panic::set_hook` 为 GUI 线程设置自定义 panic hook：
    - 捕获 panic 信息，通过消息通道紧急发送 `EngineToGui::Error("GUI 内部错误: ...")` 给引擎线程。
    - 在 hook 中尝试弹出错误对话框（`rfd::MessageDialog` 或系统原生弹窗），通知用户。
    - **不**终止进程：若为 `eframe` 框架内的 panic，`egui` 通常不会导致整个进程崩溃；若为线程级 panic，使用 `std::panic::catch_unwind` 包裹 GUI 更新逻辑。
  - **限制声明（文档中明确）**：由于 GUI 与引擎同为进程内线程，GUI 线程的未捕获 panic 可能经由 `eframe` 传递导致进程退出。本方案为"尽力隔离"，方案最佳时为错误弹窗 + 引擎继续运行；最坏时进程退出但音频已淡出静音。
  - 验收标准 A4.4 中验证"注入 panic 后引擎不中断或做出优雅降级响应"。

#### 4.2 消息通道

- 定义消息枚举（`crossbeam-channel`，使用 mutex/condvar 保证可靠性；也可选用 `std::sync::mpsc`）：
  - **术语澄清**：需求说明书中"无锁消息队列"指*不在音频回调中发送消息*（零延迟影响），而非底层数据结构无锁。GUI-引擎通信对延迟不敏感（< 1ms 即可），选用 `crossbeam-channel` 保证吞吐与可靠性。
  ```rust
  enum GuiToEngine {
      Start(EngineConfig),
      Stop,
      EnableDevice(String),
      DisableDevice(String),
      UpdateParam(ParamChange),
  }

  enum EngineToGui {
      Started,
      Stopped { stats: Stats },
      DeviceListUpdated(Vec<DeviceInfo>),
      OutputStatus(Vec<OutputStatus>),
      Error(String),
      Log(String),
  }
  ```
- GUI 线程轮询接收 `EngineToGui` 消息，更新 UI 状态。
- 消息绝对不在音频回调中发送。
- **消息通道延迟目标**：< 1ms（技术预研项，使用 `std::time::Instant` 测量）。
